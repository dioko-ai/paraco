# Practical codebase audit — 2026-09-21

Reviewed commit: `d05615a44bf9d67c5e0b7282f888a1cd3c9f79c7`.

**Keep the core architecture. Pause feature expansion and repair the integration
between its parts.** There is no evidence here that a rewrite would help. There
are, however, reproducible failures in basic launch, AI, and distribution paths.
The current checkout is not a working baseline for the functionality described
in the README.

This review read `spec.md`, the broader local `base_spec.md`, the implementation,
tests, examples, and development/release plans. It checked the source against the
owner's goals: standalone open source, no feature flags or commercial gating,
and limited complexity. Only this report was added; application code was not
changed. Temporary probes exercised the existing modules and binary.

## What fits the intended project

- One Rust crate, a small embedded Deno adapter, and a plain JavaScript dashboard
  are reasonable choices. There is no framework or service sprawl.
- The web-standard `fetch(Request, context)` contract is small and understandable.
- No runtime feature flags, account requirement, subscription checks, license-key
  checks, or cloud dependency were found in the reviewed implementation. The
  repository contains an Apache-2.0 license and contribution instructions.
- Capability declarations, credential grants, management authentication,
  concurrency limits, restart policy, and explicit service installation are
  legitimate permissions or operating settings. They should not be removed as
  “gating.” Cargo dependency features and normal CLI options are not product
  feature flags.
- Manifest validation, explicit subprocess ownership, bounded log queues,
  separate management access, and real-process acceptance tests are useful
  foundations. They need to be connected and exercised consistently.

## Findings, in repair order

### 1. P1 — Every app launch stalls before Deno starts

Locations: [runner.rs](../src/runner.rs), `launch`, lines 248 and 334–337;
[guardian.rs](../src/guardian.rs), `supervise`, lines 104–113.

The host serializes bootstrap JSON without a newline, writes it to the guardian,
and retains the pipe as the lifetime signal. The guardian calls
`read_until(b'\n')`. Neither a newline nor EOF arrives, so it never launches Deno.
This path is shared by `run`, `serve`, and `run-prepared`.

**Reproduced:** an absolute fake Deno executable reported the expected version
and would record any launch. `run examples/hello` exited after approximately 15
seconds with `application did not start within 10 seconds`; Deno was never
invoked. This demonstrates the framing bug independently of Deno availability.

**Repair:** define the bootstrap framing once, send the required delimiter, and
verify a real request and bounded cleanup through the public CLI.

### 2. P1 — Development runtime resolution contradicts the guardian contract

Locations: [runtime.rs](../src/runtime.rs), lines 43–52;
[guardian.rs](../src/guardian.rs), lines 135–140.

The development resolver returns the relative path `deno`. The guardian requires
an absolute path to an existing file. Fixing bootstrap framing alone therefore
will not make the documented PATH-based development launch work.

**Reproduced:** supplying a correctly delimited bootstrap to the guardian with
`PARACO_GUARDIAN_DENO=deno` returned `invalid pinned guardian Deno runtime`.

The resolver also treats any executable whose parent is named `bin` as a release
bundle. A conventional `cargo install --path .` installation consequently requires
bundle metadata even though it is a source installation.

**Repair:** resolve PATH to an absolute executable before starting the guardian;
identify bundles explicitly instead of inferring them from a directory name.

### 3. P1 — The documented AI example cannot obtain its grant

Locations: [runner.rs](../src/runner.rs), `standalone_deployment_id`;
[capability.rs](../src/capability.rs), lines 127–144;
[examples/ai-config.json](../examples/ai-config.json).

Configuration grants are now looked up using a host deployment ID, but the
example grants `ai-example`. A standalone launch creates a new timestamp-based
ID each time. There is no stable standalone ID or documented way to grant that
future ID before launching. Hosted deployments also need an explicit usable
configuration workflow for their allocated IDs.

**Reproduced:** loading the actual example app/config through `Capability::start`
with a standalone ID and making an authenticated request returned
`no permitted application or runtime AI default is configured`.

**Repair:** finish the host-owned identity-to-grant mapping and expose a usable
configuration flow. Keep authorization; do not solve this with automatic grants
or a bypass flag. Update examples and acceptance tests together.

### 4. P1 — Real AI requests panic when networking begins

Location: [capability.rs](../src/capability.rs), lines 61–65 and 79–83.

Both provider paths create a Tokio runtime with `enable_time()` but without an
I/O driver. Reqwest requires that driver. A correctly authorized request with a
readable credential reaches a panic rather than a provider result.

**Reproduced:** the existing `OpenAiProxy` with a temporary dummy secret and an
HTTPS loopback endpoint, driven by the same runtime construction, panicked with
`IO is disabled. Call enable_io on the runtime builder to enable IO.` No paid
provider or real credential was used.

**Repair:** use an I/O-enabled, long-lived runtime and test the actual capability
transport against a deterministic provider fixture. Also reconcile the SDK's
three-second timeout with the provider's 30-second timeout.

### 5. P1 — Bundle production, installation, and execution disagree

Locations: [build-bundle.sh](../scripts/build-bundle.sh), lines 18–22;
[install-archive.sh](../scripts/install-archive.sh), lines 44–56;
[runtime.rs](../src/runtime.rs), lines 6–10.

Two independent mismatches prevent the distribution flow from composing:

- The builder writes metadata including `paracoVersion`, `target`, checksums,
  and provenance. The runtime accepts only `denoVersion` and rejects unknown
  fields. A binary next to a builder-shaped metadata fixture failed with
  `unknown field paracoVersion, expected denoVersion`.
- The builder's archive root is `paraco-<version>-<target>`. The installer accepts
  only `paraco-<version>`. An archive with the builder's layout was rejected as
  an unsafe path when installed using the package version.

The runtime test uses a hand-written one-field metadata object; the installer
test uses a different archive layout from the builder. Neither catches this.

**Repair:** settle one bundle contract and test builder output through installer
and launcher. Defer additional package formats until that flow works.

### 6. P1 — The complete test suite does not compile, and fixtures have drifted

Locations: [tests/ai.rs](../tests/ai.rs), line 19;
[tests/server.rs](../tests/server.rs), lines 134–146 and 285–290;
[package.json](../package.json).

`cargo test --no-run` fails with E0063: the integration fixture omits the new
`credential_files`, `limits`, and `provider_endpoints` fields. This is independent
of Deno installation. Strict Clippy also fails on unused/unconnected code and
other diagnostics.

The server test helper still computes app hostnames from a hash of path, name,
and port. Production now uses a persisted deployment ID. Those requests will
target invalid hosts after the build and startup problems are repaired. AI
acceptance fixtures similarly retain name-based grants.

**Repair:** restore the complete suite, and have acceptance tests discover app
URLs/identities from the public interfaces. Add boundary tests for bootstrap,
bundle metadata, and granted provider requests. Passing isolated module tests
does not establish a working application.

### 7. P2 — Browser navigation policy blocks cross-origin app-link navigation

Locations: [server.rs](../src/server.rs), lines 427–438 and `dashboard`;
[management.js](../runtime/management.js), app link rendering;
[browser-smoke.cjs](../tests/browser-smoke.cjs).

The gateway rejects both `Sec-Fetch-Site: same-site` and `cross-site`, including
top-level document navigation. The dashboards link to a different app origin.
The policy does not distinguish following a link from cross-origin subresource
requests. The browser smoke test uses `page.goto` instead of clicking those links.

**HTTP-level reproduction:** requests to the actual app URL with navigation
headers returned 403 for both values. `Sec-Fetch-Site: none` passed that check
and reached app availability handling (503 because startup is broken).
Actual browser clicks were not tested; Chromium was unavailable.

**Repair:** define the permitted top-level navigation behavior while preserving
cross-app request isolation, and test dashboard link clicks in the browser.

### 8. P2 — Deployment identity is still tied to the manifest name

Locations: [state.rs](../src/state.rs), `install`, lines 64–78;
[server.rs](../src/server.rs), `serve` and `host`.

The durable map is keyed only by app name. Replacing an app directory with another
app using the same name reuses the ID, desired state, and browser origin. Removing
an entry from server configuration does not retire its deployment; `remove` has
no production caller. Once grants are configured by ID, those grants also follow
this reused identity. These consequences follow directly from the state lookup;
they were not exercised as a full browser/credential scenario.

**Repair:** define explicit host-controlled deployment identity and replacement/
removal semantics now, before users accumulate browser data or grants. A display
name should not silently decide whether code inherits an existing installation.

### 9. P2 — A failed state write changes in-memory state anyway

Locations: [state.rs](../src/state.rs), lines 80–118;
[storage.rs](../src/storage.rs), `put` and `remove_deployment`.

These operations mutate memory before committing the file. If the write fails,
the operation returns an error but the mutation remains and can be included in a
later successful commit. Server lifecycle handling does not update its inventory
on that error, so the two copies of desired state can disagree.

**Reproduced:** after installing a deployment, making `state.json.tmp` a directory
caused `stop` to fail, while `desired_running` still changed to false.

**Repair:** commit proposed state before publishing it in memory. Define the
required crash/power-loss durability as well: write-and-rename alone does not
include file/directory synchronization. Before scheduling is implemented, choose
one persistence approach; the plan currently proposes SQLite while the code
introduces separate custom JSON stores.

### 10. P2 — Preparation rejects ordinary source text as an import violation

Location: [artifact.rs](../src/artifact.rs), lines 208–233.

Import validation scans the entire source for substrings such as `../`, `file:`,
and `npm:`. It does not parse imports or resolve a dependency graph. Comments,
HTML, and ordinary application strings therefore trigger the policy. It also
rejects contained parent-relative imports between subdirectories.

**Reproduced:** adding only `// Documentation example: ../assets` to the hello
app caused preparation to reject `main.ts` before dependency caching.

**Repair:** validate resolved dependencies through Deno's tooling or a real
parser. Avoid maintaining a second approximation of JavaScript import syntax.

## Complexity to address now

The problem is partly integration drift and partly work spreading ahead of a
verified core. The project has roughly 6,000 Rust implementation lines; its size
does not justify a rewrite or more architectural layers.

- **AI:** each AI app creates its own proxy, framed TCP listener, hand-written
  HTTP listener, and join thread. Real requests construct Tokio runtimes per
  call. The supposedly global provider semaphore is actually per proxy/app.
  Prefer a shared host provider service and the HTTP stack already in the crate.
  Keep the SDK as a small client of the same authorization/routing path.
- **Storage:** `storage.rs` is compiled into the binary but has no production
  callers or app interface. Either deliver one concrete storage use case or
  remove the unused implementation until needed. Do not expand backup/restore
  APIs ahead of a usable storage capability.
- **Distribution:** one working archive is more useful now than parallel
  Homebrew, Debian, and macOS package scaffolding. Preserve necessary process
  cleanup, resource limits, and permission boundaries while simplifying.
- **Documentation:** use `spec.md` for intent and one current status document.
  README/local-lifecycle still say desired state is session-only; code persists
  it. Architecture decisions still describe shared app origins. The service
  module says it never invokes native managers although it now does. Documented
  `maxApps` is rejected; the actual configuration field is `max_apps` (reproduced).
  These contradictions make an outside contributor's job harder.
- **Verification:** exact pins in CI are useful, but requiring one exact Node
  patch version and Chromium before any Rust checks creates unnecessary local
  friction. Keep independent core checks runnable and a complete pinned CI job.
  Release acceptance criteria are sensible engineering checks, not feature gates.
