# Foundation audit — 2026-09-18

Paraco has a credible early runtime foundation. Keep Rust, supervised Deno
processes, the web-standard application entrypoint, and the standalone-first
boundary. Change the next milestones before these early implementation choices
become public contracts. This is an architectural and implementation review, not
a security certification or verification of platforms other than Linux.

The review covered `base_spec.md`, the public `spec.md`, the implementation,
examples, tests, and development/release documentation. No implementation or
roadmap changes were made as part of this audit.

## What is already working well

- The runtime has no cloud/account dependency. Cloud work is appropriately deferred.
- Applications use `fetch(Request, context)`; Deno owns the host entrypoint.
- Manifest validation rejects unknown fields and escaping entrypoints.
- Requested AI capabilities and host grants are separate. The transport supplies
  authenticated caller identity; request payloads cannot choose another caller.
- Browser management has a separate origin and bearer credential, restrictive
  browser headers, bounded requests, and text-only rendering of app output.
- Lifecycle workers serialize changes, reject stale generations, clean up failed
  launches, and implement bounded, cancellable recovery.
- Logs have bounded storage, rotation, launch identifiers, and defensive Unix
  file handling. Tests exercise real subprocesses, timeouts, failure isolation,
  management authorization, and cleanup, rather than only mocks.

## Decisions to change now

### 1. Decide app browser isolation before stabilizing URLs or persistence

All apps are mounted under `/apps/<name>/` on one origin. An app's browser script
can read another app's HTTP responses and use the same localStorage/IndexedDB
namespace. Cookie paths do not establish an app security boundary. This is
honestly documented in [local hosting](local-hosting.md), so it is a known scope
limit rather than an undisclosed sandbox promise. Nevertheless, it conflicts
with growing toward independently installed apps and separately granted
capabilities.

Choose a stable per-deployment origin strategy now, retain the separate management
origin, and test cross-app reads, storage, cookies, and service-worker behavior
in real browsers. Different ports separate DOM/storage origins but do not by
themselves separate cookies; evaluate hostname and cookie policy together.
Browser origin isolation also does not replace server-side authorization or
process isolation. Keep a clear trusted-local-code policy until stronger
boundaries are implemented.

Changing origins after users accumulate browser data creates a migration problem.
This is the most consequential early app-facing decision. Browser behavior is
described in [MDN's same-origin policy documentation](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy).

### 2. Move platform verification and runtime pinning out of “installation last”

The release plan targets macOS/Linux on ARM64 and x86-64. Windows has some code
paths but no working CLI lifecycle transport: `src/control.rs` returns an error
for those commands outside Unix. Both main runtime integration suites are
entirely `cfg(unix)`. There are no tracked CI workflows. Consequently, the current
evidence establishes Linux behavior, not a supported multi-platform product.

Declare the initial support matrix explicitly, including whether Windows is
first release or deferred. Add native CI for intended systems now; start with
build and real launch/request/shutdown tests and expand architecture coverage.
Extract only the platform boundaries needed for control transport, directories,
process ownership, and service integration. Keep lifecycle semantics shared.

`src/runner.rs` resolves an arbitrary `deno` from PATH; Cargo declares neither a
minimum Rust version nor a repository toolchain pin. Pin tested development/CI
versions now and make a minimal private-Deno archive early. Native installers,
signing, and distribution channels can still follow later. A clean-machine
archive smoke test is an architectural check, not merely release polish.

### 3. Define dependency preparation and offline startup

The launcher writes the host adapter into a temporary directory, supplies a fresh
temporary `DENO_DIR` on every launch, and does not explicitly select the app's
configuration or lockfile. A fixture with a valid app-local `deno.json` import
alias failed with `Import "local-alias" not a dependency` on Deno 2.9.7.

This leaves realistic app dependencies underspecified. Disposable caches do not
provide a durable offline dependency strategy, even though dependency-free
examples work offline.

Define an explicit preparation/install step that resolves and locks dependencies
into a host-owned cache or vendored artifact. Execution should consume that
prepared artifact with a deliberate configuration/import policy and no implicit
downloads. Decide whether Paraco supports Deno configuration or a smaller portable
subset, then validate that choice. Test dependency-bearing apps after deleting
ambient caches and removing network access.

Do not infer import policy solely from `--allow-net`. Deno documents imports
separately from runtime network operations in its
[security documentation](https://docs.deno.com/runtime/fundamentals/security/).
A separate audit probe importing a JSON fixture outside the app directory was
correctly denied by the current dynamic host loader; this review did not confirm
an out-of-directory import bypass.

### 4. Design durable identity and recovery before service registration

`src/server.rs` initializes every configured app to desired `running` on startup.
App name currently serves as manifest identity, route key, grant key, and log
filter; the gateway port identifies the CLI endpoint. These are useful prototype
shortcuts, but weak foundations for installations, multiple deployments of the
same app, renaming, upgrades, and durable stopped state.

Define application/package identity, local deployment identity, and runtime
identity before persisting more state. A small versioned store should separate
desired state, observed state, grants, configuration, installed versions, and
app-owned data. Do not persist PIDs as authoritative identity. Establish atomic
writes/migrations and restart reconciliation; no distributed controller is needed.

Service support also needs recovery after abnormal termination. Killing the Rust
supervisor in an isolated probe left its Deno child present. The Unix control
socket is removed only during normal cleanup and an existing socket deliberately
blocks startup. This is safe against blindly replacing a live socket, but leaves
unattended recovery incomplete. Define child ownership and verified stale-endpoint
recovery for each supported platform before advertising reliable background use.

### 5. Establish the open-source contribution and compatibility contract

The tracked tree has no project LICENSE, CONTRIBUTING guide, SECURITY policy, or
CI configuration. The release plan explicitly leaves license selection open.
Choose the license before inviting outside contributions, add package license
metadata and redistribution notices, and document contribution and private
security-reporting paths. License choice belongs to the project owner.

The manifest has no schema version and the example handwrites its own Context
interface. Add a deliberately small versioned manifest contract, JSON schema,
shared TypeScript application/capability types, and type-checking. Define the
portable API subset and a conformance fixture before adding a second backend.
An engine-agnostic signature is a good start, but is not evidence of portability
on its own. A second production backend can remain deferred.

### 6. Prove useful local applications before expanding the AI surface

The current examples prove HTTP and fake AI, but neither needs durable data or
configuration. Those are central to the product thesis. Move one useful stateful
application ahead of broad provider coverage: install, configure, grant access,
use, stop, restart the runtime, update, and remove it while preserving data.

Retain the tested AI routing policy. Before real providers, separate policy,
provider execution, and transport. The current per-app listener handles calls
serially; the adapter limits responses to 64 KiB and closes calls after three
seconds. These are appropriate fake-provider limits, not the streaming contract.
The gateway's thirty-second total request deadline also needs deliberate handling
for long responses. Add bounded concurrency, cancellation, stream handling, and
credential rotation together with a narrow real-provider increment. Keep SDK and
HTTP access on the same authorization path.

## Concrete defects and coverage gaps

| Finding | Evidence and consequence | Next action |
| --- | --- | --- |
| Shutdown can wait indefinitely on console output | `src/runner.rs` writes synchronously to parent stdout/stderr, then joins those threads in `Drop`. A fixture flooding an undrained stdout pipe kept Paraco alive more than eight seconds after SIGTERM. | Decouple draining child pipes from slow sinks; bound queues and shutdown, with explicit loss accounting. Add a blocked-sink regression test. |
| Runtime death leaves cleanup unfinished | A killed supervisor left its Deno child present; control sockets have normal-drop cleanup only. | Verify child termination and restart reconciliation after forced parent death, including stale sockets and temporary resources. |
| App import configuration is not selected | App-local import-map alias fixture failed while using the temporary host adapter. | Implement an explicit app dependency/configuration contract. |
| Gateway host is not canonicalized as documented | A request with `Host: localhost:<port>` reached the app as `http://localhost:<port>/`; `src/server.rs` forwards Host. Documentation promises `127.0.0.1:<port>`. | Normalize the host or intentionally revise the contract, and test both aliases. |
| Tests share an ambient control endpoint namespace | The first unsandboxed full run failed on an occupied `/tmp/paraco-control-1001/<port>.sock`; all tests passed with an isolated TMPDIR. | Isolate test control directories and avoid treating free TCP ports as proof of free control endpoints. |
| Browser behavior is only partly verified | JavaScript tests use a simulated DOM. | Add a small real-browser suite for origin boundaries, authorization, refresh, logs, keyboard interaction, and layout. |

Other issues worth addressing incrementally: README/local-hosting prose still
describes some shipped logs/retry features as future work; clarify which spec is
normative. Extract supervisor logic from `server.rs` as it grows, keeping transport
handlers thin. Use typed domain errors/status values as public APIs stabilize.
Avoid premature crate/plugin proliferation.

Benchmark idle memory, CPU, thread count, launch latency, and log pressure at
1/10/50 apps before changing engines or concurrency models. Current per-app Deno
processes, output threads, polling workers, and serialized log writes deserve
measurement; this audit did not establish a performance failure. Resource quotas
remain necessary before stronger untrusted-app hosting claims.

## Recommended milestone order

1. Decide support matrix, trust/origin model, license, and schema/identity basics;
   add pinned native CI.
2. Fix blocked-output shutdown, abnormal-termination recovery, and gateway contract
   drift; isolate test resources.
3. Prepare reproducible dependency-bearing apps and a minimal bundled archive;
   prove clean-machine/offline startup.
4. Add durable deployment state, configuration/data capabilities, and one useful
   stateful example; then verify OS service operation and management rediscovery.
5. Add a narrow real AI provider with streaming/cancellation, then expand local
   capabilities and installation channels according to actual app needs.

Keep cloud orchestration, catalogs, a generic plugin framework, and additional
execution engines deferred. Nothing found justifies replacing Rust or Deno.

## Verification performed

On Linux x86-64 with Rust 1.96.1 and Deno 2.9.7:

- `cargo fmt --check` passed.
- `cargo clippy --offline --all-targets -- -D warnings` passed.
- `node --test tests/management.test.cjs` passed.
- `cargo test --offline`, with Deno on PATH and an isolated TMPDIR, passed all
  71 reported tests. Six log unit tests are also included in the server test
  binary, so this count includes duplicated execution.
- Initial sandboxed networking was denied; the suite was rerun with local
  networking permitted. The initial unsandboxed run encountered the control
  endpoint collision described above.
- Temporary fixture probes checked import aliases, outside-app imports,
  forwarded Host, forced supervisor death, and blocked console output. All probe
  process groups were terminated during cleanup.

macOS/Windows execution, release artifacts, real-browser behavior, real AI
providers, dependency-vulnerability scanning, and load benchmarks were not
verified. Passing existing tests does not cover the newly identified failures.
